# apps/ui

The Next.js UI, built as a static export and run in the Tauri webview (or, for
development and testing, a plain browser). Three panes: navigation on the left,
the current entity in the middle, open secondaries on the right.

## Data

- **The UI holds its own replica of the graph**: `crates/wasm` compiled to
  WASM, loaded from a snapshot at startup. Every query is answered locally and
  every edit applies locally; the shell is sent updates a moment later. Nothing
  the user types waits on IPC.
- **`lib/graph.ts` is the one place that touches the replica.** Reads are kept
  until the next edit (every edit clears the cache), so what a component reads
  is stable between edits. **Typing notifies subscribers after a pause and
  structure changes notify at once**, so a block isn't rebuilt per keystroke;
  `settle()` delivers a pending notification, and runs before a block stops
  being edited so it never shows its old text.
- **Backends** (`backend-tauri.ts`, `backend-memory.ts`) are chosen at runtime.
  A backend may `subscribe` to what other devices change: the shell sends it
  on a channel and `Graph.receive` imports it and tells views at once, without
  pushing it back: `Replica.import` says what it brought, and `receive` moves
  the pushed version past it. A replica that joined a compacted graph has no
  history to send, so sending from before what it was given would fail for
  ever. The memory backend plays another device through
  `window.__quiddityRemote`, for `e2e/remote.spec.ts`, and keeps what the
  shell would have been told (the block being edited, and what each push was
  typed in) for `e2e/focus.spec.ts`. **`Graph.focus`/`blur` report the block
  being edited**, flushing first so the shell has the typing before the move;
  a push says which blocks it was typed in only if nothing but typing changed.
  Outside the app the graph is a made-up one in memory, built through the same
  replica, and reset on reload. **Its IDs differ on every load**, so tests
  can't keep an ID across a reload, and anything remembered by ID (Recents)
  must cope with it no longer existing.
- **A published build** (`QUIDDITY_STATIC_GRAPH=<snapshot file>`, written by
  `quiddity-node snapshot`, read by `next.config.ts`) copies it into `public/`
  as `graph.loro` and
  picks `backend-static.ts`, which fetches it; `QUIDDITY_BASE_PATH` is where the
  site is served from (GitHub Pages uses `/quiddity`). It is gated on a
  build-time `NEXT_PUBLIC_` variable, so without it the static backend isn't in
  the bundle and the Tauri build is unchanged. Edits stay in the page. Raw
  `href`s need the base path adding (`Link` and `router` do it themselves); the
  graph view's nodes are the only ones. `mise run docs` builds the site from
  `docs/`; `.github/workflows/pages.yml` does the same and deploys it.
- `lib/wasm` is generated by `pnpm ui wasm` and not committed. `dev`, `build`
  and `typecheck` run it first.

## Recovery

`components/recovery.tsx` covers the page when the app couldn't open the
graph on disk (`docs/Recovery.md`). It asks the backend `startupProblem`
before the graph boots, so it doesn't depend on it; **`chooseBackend` is the
one choice of backend, shared with `bootGraph`.** Only the Tauri backend has a
problem to report. The memory backend plays one with `?damaged`, and
`?damaged=stubborn` makes going on fail. It is read once, since the page
redirects from `/` and loses the query; going on drops the parameter and reloads the page, which then has no
problem, as the shell's cleared one wouldn't. A failure to ask is logged at
info and ignored: it is no reason to cover a working page.

## Devices

`/devices/` (an entrypoint) is where another device is added. **A backend may
have `deviceId` and `allowDevice`**, which only the Tauri backend does:
`Graph.canPair()` says, and without it the page says it needs the app. The ID
is asked for once (`Graph.deviceId()` hands back the same promise, to `use`).
The list of devices is the graph's own, from `graph.devices()`, so it updates
as the shell's does. `allowDevice` rejects with the shell's reason (not an ID,
say), which the page shows. The memory backend makes up an ID and records
what it was asked to allow in `window.__quiddityRemote.allowed`, for
`e2e/devices.spec.ts`. The populated list has no browser test: the made-up
graph records no devices.

## Sync indicator

A cloud with a coloured dot, left of the search button
(`components/sync-indicator.tsx`), links to the Devices page. **A backend may
have `subscribeStatus`**, which tells the page how this device stands (`alone`,
`offline`, `behind`, `synced` or `present`; `docs/Sync status.md`); the graph
keeps the latest, and the indicator draws nothing until a backend has said, so
the published site, which can't say, shows none. The memory backend says
`alone` and lets a test say any other through
`window.__quiddityRemote.setStatus`, for `e2e/sync-status.spec.ts`. **Each
state has a label, which is its accessible name, and a colour**; the tests
check both, and that the colours differ.

## Joining

**A replica with no history is left alone** (`Replica.isBlank`): `Graph.begin()`
makes today's page, and forgets that edit for undo, only once there is a graph,
on load or when the first updates arrive. An edit made in a blank replica
rests on history the graph it joins cannot have, and a compacted device then
refuses it. The memory backend plays such a device with `?blank`.

## Looks

- **Colours are named for their job** (`bg-surface`, `text-ink-muted`, `border-border`, `text-link`, `text-danger`), declared once in `app/globals.css` with a light and a dark value. **Don't write a palette colour (`slate-500`) or a `dark:` pair in a component**: add or change a token. `ink-muted` is for hints on the page's own ground only; on a sidebar use `ink-secondary`.
- **The repeated pieces are in `components/ui.tsx`**: `Button`, `Input`, `ErrorLine`, `Kbd`, and the class strings for links, section headings and small header buttons. Use them rather than retyping the classes. `docs/Design language.md` has the reasoning.
- **Focus, touch and motion.** A base rule draws the focus ring, so don't remove an outline without drawing one. Use the `coarse:` variant to make a target 44px on a touch screen and `no-hover:` for anything that would otherwise be revealed only by hovering. Use `motion-safe:` for any animation.
- **Floating layers** (the search panel, the link list, an overlaid pane) share `shadow-overlay`, the page's ground and a hairline border, and sit at `z-(--z-overlay)` and its siblings rather than a bare number. Colours go in `globals.css` and nowhere else, which includes what a canvas or CodeMirror draws (`var(--selection)`).
- **Type and widths.** A page's title, a section and a subsection are `pageTitle`, `sectionTitle` and `subsectionTitle` in `ui.tsx`; a page's text is `max-w-measure-text`, `-form` or `-table`. Monospace text is `font-mono`, which is JetBrains Mono NL (bundled in `app/fonts`, with its licence).

## Files

Dropping or pasting a file on the main pane keeps it and adds it to the page as
a blob block, with no page of its own.
**A backend may have `putBlob` and `getBlob`**, which only the app does
(`Graph.canKeepFiles()`): `Graph.addFile` hands the bytes to the shell, gets
their hash back, and then `attachBlob` adds the block as one edit. The UI
never writes the `##blob` line: Rust does.

- **`useFileDrop` puts its handlers on the `<article>` itself**, not a wrapper:
  the specs, and the outline's styling, find the blocks as `article > ul`. They
  are capture-phase and stop the event, because CodeMirror would otherwise read
  a dropped file as text and put it in the block. Text has no files, so it is
  left alone. The graph is fetched when a file arrives (`bootGraph()`), so the
  article doesn't suspend on it.
- **`BlobFile` draws a blob block's file** (`Block.blob`) from an object URL,
  made when the bytes are read and revoked when the page moves on.
  `RenderedBlock` draws it above the block's caption, which is the text after
  its first line, and leaves the block's own `##blob` chip out; a block with a
  file keeps its bullet. `getBlob` rejects if this device
  doesn't have the bytes yet, and the page says so with a Try again; they
  arrive from other devices by themselves, but nothing tells the page.
- **The memory backend keeps files in a map by SHA-256**, not the BLAKE3 the
  app uses: nothing outside the page checks, and the browser has no BLAKE3.
  `__quiddityRemote.createBlob` plays another device that has added a file to a
  page whose bytes this one doesn't have, and `kept` lists the hashes kept, for `e2e/files.spec.ts`.
- Playwright's `dispatchEvent("paste", …)` doesn't make a `ClipboardEvent`:
  make one in the page. A `drop` works as it is.

## Routing and boundaries

- **View state is the URL**: `/entity/?id=<main>&open=<a>,<b>` (`lib/nav.ts`).
  A static export can't enumerate entities for path segments, and the right
  pane is a list, not a route.
- **`/` is `Home`, which redirects once the graph has loaded**, at about the
  moment the sidebar's links start working. A link followed first is the
  person's choice, and the redirect, being later, would take over the
  navigation still under way, so `Home` notes links followed before its first
  redirect and stands down. `e2e/pages.spec.ts` follows the link the moment it
  is drawn, with the destination slow, to hold the race open.
- Reading the URL suspends, so each pane, and each secondary within the right
  pane, has its own `Suspense` and error boundary (`Region`): a slow or broken
  one holds up nothing else. A card's header sits outside its content's
  boundary so it can always be closed.
- **The graph only exists in the browser**, so everything that reads it (the
  page, and both sidebars) renders inside `ClientOnly` and isn't prerendered.
  A static export never renders them on a server, but **`next dev` does, on
  every request**: a pane left outside `ClientOnly` works in the export and
  fails in development with a server error. The `e2e-dev` tests exist for
  this.

## Editing

- **`EditableOutline` provides an `Editing` context** (which block is being
  edited, where the caret goes, the entity's blocks in reading order); an
  `Outline` outside one, such as in references, is read-only.
- **`BlockEditor` is a CodeMirror editor bound to one block.** What is typed
  goes in as the splice that was typed, last change first so offsets stay
  valid; changes from the graph come back as the smallest edit, marked
  `fromGraph` so they aren't sent again. **It reconciles against
  `graph.blockText`, never against props**, which can be a keystroke behind.
- **Keys act on the graph, then say where editing continues.** Moving blocks
  makes React remount them, so a key that moves the block being edited calls
  `edit(id, caret)` *before* the structural change so the new editor opens at
  the right place. Undo and redo are the graph's (`Mod-z` in the editor, and
  `UndoKeys` when no editor is focused); there is no editor-level history.
- Removing a focused editor fires a blur that isn't the user leaving, so
  `closing` is set in a layout effect (which runs before the DOM goes).
- IDs held by editing state go dead across an undo of a deletion; that just
  ends the edit.

- **Leaving a block saves it** (`EditableOutline`): it remembers each block's
  text from when editing began and calls `graph.commitBlock(id, before)` when
  editing moves on or the page is left. That is what makes an entity for a
  `[[link]]` the edit added, and renames one a moment-old link made if the
  link is corrected. A link to nowhere that is already in a block (written on
  another device, or left by an undo) is a link (`NewEntityLink`, an `<a href="#">` drawn like any other), and
  following it makes the entity (`graph.followLink`).
- **Links are completed in the editor** (`lib/link-completion.ts`, with
  `lib/auto-brackets.ts` pairing `[`). Its keys sit above the outliner's, so
  in a link the arrows and Enter are the list's; **Escape is left to the
  outliner** unless an entry is chosen, or leaving the block would no longer
  save it. The list opens only on a user edit that touches the link (never a
  `fromGraph` change, never just the caret arriving), and choosing an entry
  writes it into the link, marked `previewing` so it doesn't reopen the list.
  Enter with no list follows the link. A hit's `link` is the text to write,
  escaped and qualified by Rust.
- **A property chip's key goes to the entity that defines the property**
  (`Property.definition`). With none yet it is a button, and following it
  makes the entity (`graph.defineProperty`), as a link to nowhere does. **A
  tag's chip (`inline`) goes to the entity it names** instead, and with none
  makes it as a link does (`graph.followLink`): a tag is a link, not a property. A block
  of nothing but properties is drawn as chips with its bullet hidden, not
  removed, so the chips line up with the text around them.
- **Meta-properties** (`meta-sections.tsx`): flags with no chip go under the
  title, and Inherited and the inverse trees go below the body. A chip with
  `flags` is ringed and carries `data-flagged`, with the reasons as its
  title. All the words come from Rust.
- The main pane's title (`EditableTitle`) renames in place when the entity
  is `renamable`: Enter or leaving the field keeps it, Escape drops it. Side
  cards and the journals feed show plain titles.

## Graph view

`/graph/` (an entrypoint) draws `graph.connections()` with d3: `d3-force` lays
it out, `d3-zoom` pans and zooms, `d3-drag` moves nodes. **It is drawn on a
`<canvas>`**: an element per node and edge moved on every tick was slow. **d3
owns the canvas and a `sr-only` list beside it; React owns the elements and
calls `draw()` once on mount and `update(data)` when the graph changes.**

- **Painting** is one function, `paint`, reading the nodes, links and view as
  they are; anything that changes them asks `repaint()`, which coalesces to one
  paint per animation frame and does nothing while the page is hidden. Colours
  are the theme's (`--graph-link`, `--graph-node`, `--graph-node-stroke`, `--graph-label`), read
  from the stylesheet because a canvas can't take them from a class, and read again
  when `prefers-color-scheme` changes. The
  backing store is scaled by `devicePixelRatio`, and **everything is sized in
  CSS pixels**: the canvas transform is `ratio·k`, so a retina display gets
  sharper output, not bigger nodes. The ratio is re-read when the canvas
  resizes and when a `(resolution: …dppx)` query stops matching (moving
  between screens, browser zoom).
- **Sizes live in `lib/graph-style.ts`.** Node radii are in graph space and
  scale with the zoom (`max(3, 3·ln(degree+1))`); **text and line widths are
  held at a size on screen** by dividing the zoom out (`1 / view.k`), so a
  label is 10px whatever the zoom. Don't put a font size or line width in
  graph units.
- **Hit-testing is ours** (`nodeAt`): the nearest node within its radius, in
  the canvas's pixels. The zoom's `filter` refuses a press on a node so the
  drag gets it, `d3-drag`'s `subject` is `nodeAt`, and hover, click, Alt-click
  and double-click on the background all use it. **A press starts a drag, but
  nothing is disturbed until the pointer moves**, or a click would stir the
  layout.
  **`d3-drag` reports a drag in the subject's coordinates**, so the subject is
  where the node is in canvas pixels (not in graph space), or a grabbed node
  jumps by the view's offset.
- **The accessible graph is the list of real `<a href>` links** (click opens
  the entity, shift-click opens it at the side; focus highlights the node on the
  canvas), and the canvas is `aria-hidden`. They are not positioned, which is
  what makes them free. They carry `data-x`/`data-y` only when the layout is
  still, and the canvas carries `data-view` and `data-settled`: tests read
  those (and `data-grabbed`, where a drag has the node, in canvas pixels), and
  click the canvas where the node is. Don't rely on them elsewhere.

- **Positions and the view are remembered** (`lib/graph-layout.ts`, in memory
  and in localStorage), so leaving and coming back finds everything where it
  was. They are saved when the layout settles, after a zoom and on leaving, and
  **nothing is saved before the first nodes are drawn**: setting the initial
  zoom ends a zoom, which would otherwise wipe the layout about to be
  restored. Entities with no position are placed beside one they link to.
  **Entities that have a position are held (`fx`/`fy`) while the new ones find
  theirs, then let go when the layout ends**: otherwise the link force pulls a
  settled layout towards its rest length on every load. With nothing new the
  simulation is stopped (d3 starts one running, at full heat, as it's made). Entities placed by an unfinished run stay free
  across a second `update`. Positions of entities that have gone are dropped
  when next saved.
- Dragging lets every node go at the start, so the rest untangles around the
  dragged one, and the dragged node on release (nodes aren't pinned).
- Link strength is d3's default (1 over the fewer links of the two ends), so a
  link between hubs is slack. Don't set a flat strength.
- **Framing** (`lib/graph-fit.ts`): with no remembered view the graph is framed
  once at the first draw and again, animated, when the layout settles, until
  the person pans or zooms (`tracking`). It frames the largest connected group
  (every entity when nothing is linked), so loose entities don't shrink the
  view. **Reset view** and a double-click on the background do the same.
  Alt-click frames a node and its neighbours instead of opening it. The animation is
  `d3-transition`, imported for its effect on selections (it works on a canvas
  selection as on any other); a pan or zoom by the person interrupts it.
- Labels are not drawn when a node is under `LABEL_DIAMETER` (5px) across
  on screen, except for the node hovered or focused. The canvas carries
  `data-labels`, how many the last paint drew, for tests.

## Search

The action strip above the main pane holds the search button; **Cmd/Ctrl-K**
(captured, so a focused editor can't take it) opens the panel
(`components/search.tsx`).

- **A panel is a list of `Facet`s** (`lib/search/facet.ts`), one section each,
  in order. A facet is `search(query, graph) => Hit[] | Promise<Hit[]>`, best
  first. `useSearch` runs them independently and keeps each one's latest
  answer, so a slow facet (full text, embeddings) never holds up a fast one
  and an old answer stays until its replacement arrives.
- **Make new facets by composing**: `limited(n, facet)`, `when(applies, facet)`
  (a prefix such as `>` that selects actions, say). A hit's `target` is data
  (`entity`, or `run`), not a callback, so hits can be ranked and logged later.
- **Matching lives in Rust** (`quiddity-view`'s `search.rs`, where it is
  mutation-tested), reached through `graph.searchTitles`. Facets only shape
  its answers into hits.
- **The Text facet** (`search_text`) is BM25 over every block: all the words
  must be there and the last may be unfinished, so `note` finds `notes` while
  `not loro` doesn't. It shows the stretch of the block around the first match.
  An entity's own name belongs to the Pages facet, not this one.
- The graph's `searchTitles` and `searchText` aren't cached: the panel asks per keystroke and
  an answer is rarely wanted twice.

## All entities

`AllEntities` is a sortable table with a checkbox on each row, above a title
filter and a "Hide journals" checkbox (ticked to begin with; the rows say
`journal`, from Rust). It makes no entities: the tests make one by linking to
it from a journal block. **Selection is the set of IDs ticked, filtered by the
rows still there and shown**, so an entity that an undo or a sync removes, or
that the filter hides, simply stops counting. Deleting asks first, inline
(`role="alertdialog"`) rather than with `window.confirm`, which the Tauri
webview can't be relied on to show; **changing the selection withdraws the
question**, so what is confirmed is what was asked about. Deletion
(`graph.deleteEntities`) is one undo step, and links to a deleted entity stay
in the text as links to nowhere.

## Rendering

`RenderedBlock` is how a block reads when not being edited: `splitBlock` takes
line properties out for chips and swaps inline ones for placeholder characters,
`remarkQuiddity` turns `[[links]]`, `((refs))` and the placeholders into custom
elements (in text only, so never in code), and `react-markdown` draws the rest.
Block text comes from other devices and is untrusted, so:

- **Don't add `rehype-raw` or render HTML strings.** Raw HTML shows as text.
- Only `http(s)` and `mailto` links are links, opened through
  `lib/open-external.ts`; anything else is inert text.
- **Images aren't fetched**: a remote image is a request to its author.

## Tests

Playwright (`pnpm ui build`, then `pnpm ui test:e2e`). Most tests (`e2e`)
run against the static export; a few (`e2e-dev`) run against `next dev`, which
renders on a server as the app does in development, and also shows React
warnings that a production build hides (duplicate keys, say), which the page
logging them fails the test. Each test starts from the same made-up graph. `e2e/fixtures.ts` fails a test
if the page logs an error. Pitfalls:

- The sidebar repeats names (Favourites, Recents), so scope a link locator to
  `main` before `.first()`.
- On the in-memory graph a page reload starts over, so a test that has changed
  something must move by clicking (the sidebar), not `page.goto`.
- A block's rendered text is `[data-block-text]` and an editor is `.cm-content`.
- The page links an icon (`app/icon.svg`, a copy of the app icon's master), so
  Playwright's full Chromium doesn't ask for `/favicon.ico`, whose 404 would
  fail every test. Keep the link: without it, full Chromium needs an empty
  `favicon.ico` in `out/` and `public/` for the run.
- Typing `\n` presses Enter, which splits the block; use Shift-Enter for a
  newline. Press `Control+Shift+Z`, not `Control+Shift+z`: Playwright otherwise
  sends a lowercase `z` that no keyboard does.
