# apps/ui

The Next.js UI, built as a static export and run in the Tauri webview (or, for
development and testing, a plain browser). Three panes: navigation on the left,
the current entity in the middle, open secondaries on the right.

## Data

- **The UI holds its own replica of the graph**: `crates/wasm` compiled to
  WASM, loaded from a snapshot at startup. Every query is answered locally and
  every edit applies locally; the shell is sent updates a moment later. Nothing
  the user types waits on IPC.
- **`lib/graph.ts` is the one place that touches the replica.** Reads are kept
  until the next edit (every edit clears the cache), so what a component reads
  is stable between edits. **Typing notifies subscribers after a pause and
  structure changes notify at once**, so a block isn't rebuilt per keystroke;
  `settle()` delivers a pending notification, and runs before a block stops
  being edited so it never shows its old text.
- **Backends** (`backend-tauri.ts`, `backend-memory.ts`) are chosen at runtime.
  Outside the app the graph is a made-up one in memory, built through the same
  replica, and reset on reload. **Its IDs differ on every load**, so tests
  can't keep an ID across a reload, and anything remembered by ID (Recents)
  must cope with it no longer existing.
- **A published build** (`QUIDDITY_STATIC_GRAPH=<graph dir>`, read by
  `next.config.ts`) copies the directory's `graph.loro` into `public/` and
  picks `backend-static.ts`, which fetches it; `QUIDDITY_BASE_PATH` is where the
  site is served from (GitHub Pages uses `/quiddity`). It is gated on a
  build-time `NEXT_PUBLIC_` variable, so without it the static backend isn't in
  the bundle and the Tauri build is unchanged. Edits stay in the page. Raw
  `href`s need the base path adding (`Link` and `router` do it themselves); the
  graph view's nodes are the only ones. `mise run docs` builds the site from
  `docs/`; `.github/workflows/pages.yml` does the same and deploys it.
- `lib/wasm` is generated by `pnpm ui wasm` and not committed. `dev`, `build`
  and `typecheck` run it first.

## Routing and boundaries

- **View state is the URL**: `/entity/?id=<main>&open=<a>,<b>` (`lib/nav.ts`).
  A static export can't enumerate entities for path segments, and the right
  pane is a list, not a route.
- Reading the URL suspends, so each pane, and each secondary within the right
  pane, has its own `Suspense` and error boundary (`Region`): a slow or broken
  one holds up nothing else. A card's header sits outside its content's
  boundary so it can always be closed.
- **The graph only exists in the browser**, so everything that reads it (the
  page, and both sidebars) renders inside `ClientOnly` and isn't prerendered.
  A static export never renders them on a server, but **`next dev` does, on
  every request**: a pane left outside `ClientOnly` works in the export and
  fails in development with a server error. The `e2e-dev` tests exist for
  this.

## Editing

- **`EditableOutline` provides an `Editing` context** (which block is being
  edited, where the caret goes, the entity's blocks in reading order); an
  `Outline` outside one, such as in references, is read-only.
- **`BlockEditor` is a CodeMirror editor bound to one block.** What is typed
  goes in as the splice that was typed, last change first so offsets stay
  valid; changes from the graph come back as the smallest edit, marked
  `fromGraph` so they aren't sent again. **It reconciles against
  `graph.blockText`, never against props**, which can be a keystroke behind.
- **Keys act on the graph, then say where editing continues.** Moving blocks
  makes React remount them, so a key that moves the block being edited calls
  `edit(id, caret)` *before* the structural change so the new editor opens at
  the right place. Undo and redo are the graph's (`Mod-z` in the editor, and
  `UndoKeys` when no editor is focused); there is no editor-level history.
- Removing a focused editor fires a blur that isn't the user leaving, so
  `closing` is set in a layout effect (which runs before the DOM goes).
- IDs held by editing state go dead across an undo of a deletion; that just
  ends the edit.

- **Leaving a block saves it** (`EditableOutline`): it remembers each block's
  text from when editing began and calls `graph.commitBlock(id, before)` when
  editing moves on or the page is left. That is what makes an entity for a
  `[[link]]` the edit added, and renames one a moment-old link made if the
  link is corrected. A link to nowhere that is already in a block (written on
  another device, or left by an undo) is a button, `NewEntityLink`, and
  following it makes the entity (`graph.followLink`).
- **Links are completed in the editor** (`lib/link-completion.ts`, with
  `lib/auto-brackets.ts` pairing `[`). Its keys sit above the outliner's, so
  in a link the arrows and Enter are the list's; **Escape is left to the
  outliner** unless an entry is chosen, or leaving the block would no longer
  save it. The list opens only on a user edit that touches the link (never a
  `fromGraph` change, never just the caret arriving), and choosing an entry
  writes it into the link, marked `previewing` so it doesn't reopen the list.
  Enter with no list follows the link. A hit's `link` is the text to write,
  escaped and qualified by Rust.
- **A property chip's key goes to the entity that defines the property**
  (`Property.definition`). With none yet it is a button, and following it
  makes the entity (`graph.defineProperty`), as a link to nowhere does. A block
  of nothing but properties is drawn as chips with its bullet hidden, not
  removed, so the chips line up with the text around them.
- The main pane's title (`EditableTitle`) renames in place when the entity
  is `renamable`: Enter or leaving the field keeps it, Escape drops it. Side
  cards and the journals feed show plain titles.

## Graph view

`/graph/` (an entrypoint) draws `graph.connections()` with d3: `d3-force` lays
it out, `d3-zoom` pans and zooms, `d3-drag` moves nodes. **d3 owns the SVG
inside the `<svg>`; React owns only the `<svg>` and calls `draw()` once on
mount and `update(data)` when the graph changes**, so a node's `<a>` element is
d3's, not React's. Nodes are real `<a href>` links (click opens the entity,
shift-click opens it at the side) and are labelled by `aria-label`.

- **Positions and the view are remembered** (`lib/graph-layout.ts`, in memory
  and in localStorage), so leaving and coming back finds everything where it
  was. They are saved when the layout settles, after a zoom and on leaving, and
  **nothing is saved before the first nodes are drawn**: setting the initial
  zoom ends a zoom, which would otherwise wipe the layout about to be
  restored. Entities with no position are placed beside one they link to.
  **Entities that have a position are held (`fx`/`fy`) while the new ones find
  theirs, then let go when the layout ends**: otherwise the link force pulls a
  settled layout towards its rest length on every load. With nothing new the
  simulation is stopped (d3 starts one running, at full heat, as it's made). Entities placed by an unfinished run stay free
  across a second `update`. Positions of entities that have gone are dropped
  when next saved.
- Dragging lets every node go at the start, so the rest untangles around the
  dragged one, and the dragged node on release (nodes aren't pinned).
- Link strength is d3's default (1 over the fewer links of the two ends), so a
  link between hubs is slack. Don't set a flat strength.
- **Framing** (`lib/graph-fit.ts`): with no remembered view the graph is framed
  once at the first draw and again, animated, when the layout settles, until
  the person pans or zooms (`tracking`). It frames the largest connected group
  (every entity when nothing is linked), so loose entities don't shrink the
  view. **Reset view** and a double-click on the background do the same.
  Alt-click frames a node and its neighbours instead of opening it. The animation is
  `d3-transition`, imported for its effect on selections; a pan or zoom by the
  person interrupts it.
- Labels are hidden when a node's radius on screen is under `LABEL_RADIUS`,
  except for the node hovered or focused. `aria-label` is unaffected.

## Search

The action strip above the main pane holds the search button; **Cmd/Ctrl-K**
(captured, so a focused editor can't take it) opens the panel
(`components/search.tsx`).

- **A panel is a list of `Facet`s** (`lib/search/facet.ts`), one section each,
  in order. A facet is `search(query, graph) => Hit[] | Promise<Hit[]>`, best
  first. `useSearch` runs them independently and keeps each one's latest
  answer, so a slow facet (full text, embeddings) never holds up a fast one
  and an old answer stays until its replacement arrives.
- **Make new facets by composing**: `limited(n, facet)`, `when(applies, facet)`
  (a prefix such as `>` that selects actions, say). A hit's `target` is data
  (`entity`, or `run`), not a callback, so hits can be ranked and logged later.
- **Matching lives in Rust** (`quiddity-view`'s `search.rs`, where it is
  mutation-tested), reached through `graph.searchTitles`. Facets only shape
  its answers into hits.
- **The Text facet** (`search_text`) is BM25 over every block: all the words
  must be there and the last may be unfinished, so `note` finds `notes` while
  `not loro` doesn't. It shows the stretch of the block around the first match.
  An entity's own name belongs to the Pages facet, not this one.
- The graph's `searchTitles` and `searchText` aren't cached: the panel asks per keystroke and
  an answer is rarely wanted twice.

## All entities

`AllEntities` is a sortable table with a checkbox on each row. **Selection is
the set of IDs ticked, filtered by the rows still there**, so an entity that an
undo or a sync removes simply stops counting. Deleting asks first, inline
(`role="alertdialog"`) rather than with `window.confirm`, which the Tauri
webview can't be relied on to show; **changing the selection withdraws the
question**, so what is confirmed is what was asked about. Deletion
(`graph.deleteEntities`) is one undo step, and links to a deleted entity stay
in the text as links to nowhere.

## Rendering

`RenderedBlock` is how a block reads when not being edited: `splitBlock` takes
line properties out for chips and swaps inline ones for placeholder characters,
`remarkQuiddity` turns `[[links]]`, `((refs))` and the placeholders into custom
elements (in text only, so never in code), and `react-markdown` draws the rest.
Block text comes from other devices and is untrusted, so:

- **Don't add `rehype-raw` or render HTML strings.** Raw HTML shows as text.
- Only `http(s)` and `mailto` links are links, opened through
  `lib/open-external.ts`; anything else is inert text.
- **Images aren't fetched**: a remote image is a request to its author.

## Tests

Playwright (`pnpm ui build`, then `pnpm ui test:e2e`). Most tests (`e2e`)
run against the static export; a few (`e2e-dev`) run against `next dev`, which
renders on a server as the app does in development, and also shows React
warnings that a production build hides (duplicate keys, say), which the page
logging them fails the test. Each test starts from the same made-up graph. `e2e/fixtures.ts` fails a test
if the page logs an error. Pitfalls:

- The sidebar repeats names (Favourites, Recents), so scope a link locator to
  `main` before `.first()`.
- On the in-memory graph a page reload starts over, so a test that has changed
  something must move by clicking (the sidebar), not `page.goto`.
- A block's rendered text is `[data-block-text]` and an editor is `.cm-content`.
- Typing `\n` presses Enter, which splits the block; use Shift-Enter for a
  newline. Press `Control+Shift+Z`, not `Control+Shift+z`: Playwright otherwise
  sends a lowercase `z` that no keyboard does.
