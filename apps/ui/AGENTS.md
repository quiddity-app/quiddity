# apps/ui

The Next.js UI, built as a static export and run in the Tauri webview (or, for
development and testing, a plain browser). Three panes: navigation on the left,
the current entity in the middle, open secondaries on the right.

## Data

- **The UI holds its own replica of the graph**: `crates/wasm` compiled to
  WASM, loaded from a snapshot at startup. Every query is answered locally and
  every edit applies locally; the shell is sent updates a moment later. Nothing
  the user types waits on IPC.
- **`lib/graph.ts` is the one place that touches the replica.** Reads are kept
  until the next edit (every edit clears the cache), so what a component reads
  is stable between edits. **A read made again gives back the objects it gave
  before for whatever the edit didn't change** (`lib/share.ts`), so `memo` on a
  block can hold; a read that isn't one of the graph's own (a `Map` made in the
  selector) is made afresh each time. **Typing notifies subscribers after a
  pause, and no later than a second after the first of a run that doesn't stop;
  structure changes notify at once**, so a block isn't rebuilt per keystroke;
  `settle()` delivers a pending notification, and runs before a block stops
  being edited so it never shows its old text. **Nothing waits for typing to
  stop**: the push to the shell and the notification both use `debounce`
  (`lib/debounce.ts`), which waits for quiet but never past a maximum from the
  first call it hasn't answered. Don't write a bare `clearTimeout`/`setTimeout`
  debounce for something that must happen while typing goes on.
- **Reads that can lag an edit are deferred**: `useDeferredRead(read, deps)`
  (`lib/use-graph.ts`) reads in a deferred render, which React does after what
  the person did has been drawn and drops for what they do next. The sidebar
  and the references use it. `useRead` is for what must be right in the render
  that follows an edit (the page itself).
- **Backends** (`backend-tauri.ts`, `backend-memory.ts`) are chosen at runtime.
  A backend may `subscribe` to what other devices change: the shell sends it
  on a channel and `Graph.receive` imports it and tells views at once, without
  pushing it back: `Replica.import` says what it brought, and `receive` moves
  the pushed version past it. A replica that joined a compacted graph has no
  history to send, so sending from before what it was given would fail for
  ever. The memory backend plays another device through
  `window.__quiddityRemote`, for `e2e/remote.spec.ts`, and keeps what the
  shell would have been told (the block being edited, and what each push was
  typed in) for `e2e/focus.spec.ts`. **`Graph.focus`/`blur` report the block
  being edited**, flushing first so the shell has the typing before the move;
  a push says which blocks it was typed in only if nothing but typing changed.
  Outside the app the graph is a made-up one in memory, built through the same
  replica, and reset on reload. **Its IDs differ on every load**, so tests
  can't keep an ID across a reload, and anything remembered by ID (Recents)
  must cope with it no longer existing.
- **A published build** (`QUIDDITY_STATIC_GRAPH=<snapshot file>`, written by
  `quiddity-node snapshot`, read by `next.config.ts`) copies it into `public/`
  as `graph.loro` and
  picks `backend-static.ts`, which fetches it; `QUIDDITY_BASE_PATH` is where the
  site is served from (GitHub Pages uses `/quiddity`). It is gated on a
  build-time `NEXT_PUBLIC_` variable, so without it the static backend isn't in
  the bundle and the Tauri build is unchanged. Edits stay in the page. Raw
  `href`s need the base path adding (`Link` and `router` do it themselves); the
  graph view's nodes are the only ones. **A published build also needs the
  names** (`quiddity-node names`, as `names.txt` beside the snapshot or at
  `QUIDDITY_STATIC_NAMES`), and gives every entity in them a stable address,
  `/page/<name>/` (`docs/Page names.md`): `useView` resolves names to IDs and
  back (`lib/nav.ts` has the URL format), so a component asks it for an `href`
  and never builds one. An entity with no name in the list (a link to nowhere,
  or one made in the browser) keeps `/entity/?id=`. The route is
  `app/page/[name]/page.published.tsx`, a route only when publishing, because
  an export refuses a dynamic route with nothing to build it for, and it must be
  a server component of its own: re-exporting the client one loses
  `generateStaticParams`. `mise run docs` builds the site from
  `docs/`; `.github/workflows/pages.yml` does the same and deploys it.
- `lib/wasm` is generated by `pnpm ui wasm` and not committed. `dev`, `build`
  and `typecheck` run it first.

## Recovery

`components/recovery.tsx` covers the page when the app couldn't open the
graph on disk (`docs/Recovery.md`). It asks the backend `startupProblem`
before the graph boots, so it doesn't depend on it; **`chooseBackend` is the
one choice of backend, shared with `bootGraph`.** Only the Tauri backend has a
problem to report. The memory backend plays one with `?damaged`, and
`?damaged=stubborn` makes going on fail. It is read once, since the page
redirects from `/` and loses the query; going on drops the parameter and reloads the page, which then has no
problem, as the shell's cleared one wouldn't. A failure to ask is logged at
info and ignored: it is no reason to cover a working page.

## Graph picker

`components/graph-switcher.tsx` is the name at the head of the left pane (and in
the strip where that is a drawer): the open graph's name, a menu of the graphs
and *New empty graph…* / *New graph to sync…* (`sync` makes a blank replica).
**A backend may have `graphs`, `switchGraph` and `createGraph`**; `graphs`
returns null (or `switchable: false`) where there is one graph, and then the
name is plain "Quiddity" (or the one graph's name). **It flushes the graph
before asking the shell**, since a pending push would otherwise go to the new
graph, then `location.replace('/')`: the replica is of the old graph. The name
dialog is a portal into `body`, because the left pane is transformed and would
otherwise contain `fixed`. `useMenu` (`components/use-menu.ts`) is the keyboard and pointer handling the
More menu shares with it. The memory backend plays a library with `?graphs`,
kept in `sessionStorage` over the reload, and records requests in
`__quiddityRemote.graphRequests`, for `e2e/graphs.spec.ts`.

## Devices

`/devices/` (an entrypoint) is where another device is added. **A backend may
have `deviceId` and `allowDevice`**, which only the Tauri backend does:
`Graph.canPair()` says, and without it the page says it needs the app. The ID
is asked for once (`Graph.deviceId()` hands back the same promise, to `use`).
The list of devices is the graph's own, from `graph.devices()`, so it updates
as the shell's does. **Naming and removing a device are edits in the UI's own replica** (`graph.nameDevice`, `removeDevice`), pushed like any other, so they need no backend and work outside the app; a device's own row has no Remove, since it would list itself again on its next save. `allowDevice` rejects with the shell's reason (not an ID,
say), which the page shows. The memory backend makes up an ID and records
what it was asked to allow in `window.__quiddityRemote.allowed`, for
`e2e/devices.spec.ts`. The populated list, and so naming and removal, has no browser test: the made-up
graph records no devices (`quiddity-view` tests them).

## Sync indicator

A cloud with a coloured dot, left of the search button
(`components/sync-indicator.tsx`), a button that opens a non-modal pop-up of
details (Escape or a press elsewhere closes it) with a link to the Devices
page, which is in the More menu rather than the sidebar. **A backend may
have `subscribeStatus`**, which tells the page how this device stands as a
`SyncDetails`: the `state` (`alone`,
`offline`, `behind`, `synced` or `present`; `docs/Sync status.md`) and what it
rests on (connected devices, listed devices, blocks held back, devices here).
`SyncFacts` draws those, in the pop-up and on Stats and debug. The graph
keeps the latest, and the indicator draws nothing until a backend has said, so
the published site, which can't say, shows none. The memory backend says
`alone` and lets a test say any other through
`window.__quiddityRemote.setStatus(state, details?)`, the rest defaulting to nothing, for `e2e/sync-status.spec.ts`. **Each
state has a label, which is its accessible name, and a colour**; the tests
check both, and that the colours differ.

## More menu

`components/more-menu.tsx`, right of search in the action strip: Devices (the
entrypoints with `in: "menu"` in `lib/nav.ts`, the one list the sidebar and the
app's Go menu share) and Delete Entity for the main pane's entity
(`docs/Menus.md`).

- **Delete asks first**, inline as in All entities, with Cancel focused.
  **Confirming navigates away first and deletes once `main` has left the
  entity** (`leaving`): deleting under the main pane would have `graph.entity` fail
  and the page flashes its error boundary.
- **Show Page Graph** toggles `View.pageGraph` (`pagegraph=1` in the URL), which
  `RightPane` draws above the open cards as `PageGraph` for `main`. **It draws
  with the graph view's `draw` and `persist: false`**, so it neither restores nor
  overwrites the whole graph's remembered layout; `highlight(id)` picks out the
  entity (`--graph-current`, and `aria-current` on its link). The entities
  are `pageGraph` in `lib/page-graph.ts` (`docs/Page graph.md`). The sr-only links
  have no size, so a test focuses one and presses Enter.
- **The same component hears the app's native menu** (`lib/menu.ts`): the shell
  sends one string on the `menu` event (`delete-entity`, or `go:<path>` for an
  entrypoint; anything else is ignored), and the page tells the shell
  whether an entity is open (`set_entity_open`) so File ▸ Delete Entity is only
  on then. A browser has no menu, and both do nothing there. Go navigates as
  the sidebar's links do, so it drops the side pane.

## Stats and debug

`/stats/` (`components/stats.tsx`, in the More menu with Devices) shows
`graph.stats()` (counts, and a table of the virtual entities with their incoming
links) and the result of `graph.check()` (`docs/Stats and debug.md`).

- **The Sync section** spells out the sync indicator's state (`states` is
  exported from `sync-indicator.tsx`, with what each means) and counts the
  devices the graph lists. Without a status (the published site) it says the
  build can't sync.
- **The Sync section also shows this device's ID and the network log**
  (`SyncDetails.device` and `.log`, newest first, with Copy log), from
  `Peer::events` (`docs/Network log.md`). The memory backend's `setStatus`
  takes `device` and `log` in its details.
- **The check runs when asked, not on render**, because it reads the whole graph
  again. The page keeps the result with the revision it was run at, and says
  when the graph has since changed; it doesn't rerun by itself. A failure of
  the check itself is shown, not thrown, so it doesn't take the page's boundary.
- **Each outcome says Passed or its problem count in words**, so it doesn't
  rest on colour; a problem with an `id` is an `EntityLink`, which takes a `~`
  ID too.
- The virtual entities are drawn 100 at a time (`Show more`): a real graph links
  to thousands of names. The Rust side already orders them.
- `e2e/stats.spec.ts` leans on the made-up graph: `merges::` is a key no entity
  defines, so `~merges` is virtual, and a test makes `Fresh` by linking to it.

## First run and joining

`components/welcome.tsx` covers the page on a device with no graph and asks
whether to start one or join another's (`docs/First run.md`); `Joining`
(`components/joining.tsx`) covers it while a device that chose to join has no
history, with its ID, the add-a-device form and the network log (it reuses
`ThisDevice` and `Add` from the Devices page and `NetworkLog`). Both are
mounted in the layout beside `Recovery`, ask the backend (`firstRun`, `start`,
`joining`: only the app has them) before the graph boots, and draw nothing
otherwise. **Joining is the first button, and the focused one**: it is the
choice that can't make a graph that won't merge. The memory backend plays them
with `?firstrun` (`=stubborn` fails to go on) and `?joining`; choosing Join
there reloads into `?blank&joining`, as the shell's blank graph would be.
`e2e/welcome.spec.ts`.

**A replica with no history is left alone** (`Replica.isBlank`): `Graph.begin()`
makes today's page, and forgets that edit for undo, only once there is a graph,
on load or when the first updates arrive. An edit made in a blank replica
rests on history the graph it joins cannot have, and a compacted device then
refuses it. The memory backend plays such a device with `?blank`.

## Looks

- **Colours are named for their job** (`bg-surface`, `text-ink-muted`, `border-border`, `text-link`, `text-danger`), declared once in `app/globals.css` with a light and a dark value. **Don't write a palette colour (`slate-500`) or a `dark:` pair in a component**: add or change a token. `ink-muted` is for hints on the page's own ground only; on a sidebar use `ink-secondary`.
- **The repeated pieces are in `components/ui.tsx`**: `Button`, `Input`, `ErrorLine`, `Kbd`, and the class strings for links, section headings and small header buttons. Use them rather than retyping the classes. `docs/Design language.md` has the reasoning.
- **Focus, touch and motion.** A base rule draws the focus ring, so don't remove an outline without drawing one. Use the `coarse:` variant to make a target 44px on a touch screen and `no-hover:` for anything that would otherwise be revealed only by hovering. Use `motion-safe:` for any animation.
- **Floating layers** (the search panel, the link list, an overlaid pane) share `shadow-overlay`, the page's ground and a hairline border, and sit at `z-(--z-overlay)` and its siblings rather than a bare number. Colours go in `globals.css` and nowhere else, which includes what a canvas or CodeMirror draws (`var(--selection)`).
- **Type and widths.** A page's title, a section and a subsection are `pageTitle`, `sectionTitle` and `subsectionTitle` in `ui.tsx`; a page is drawn in `Page` (`width="text"`, `"form"` or `"table"`), which sets the text size that grows with the pane, the same as an entity's, and the titles are in `em` so they follow it. Don't set a font size on a page's article. Monospace text is `font-mono`, which is JetBrains Mono NL (bundled in `app/fonts`, with its licence).

## Files

Dropping or pasting a file on the main pane keeps it and adds it to the page as
a blob block, with no page of its own.
**A backend may have `putBlob` and `getBlob`**, which only the app does
(`Graph.canKeepFiles()`): `Graph.keepFile` hands the bytes to the shell and
gets their hash back, and then `Graph.attachFile` adds the block as one edit.
`useFileDrop` keeps a few files at once but attaches them in order. The UI
never writes the `##blob` line: Rust does.

- **`useFileDrop` puts its handlers on the `<article>` itself**, not a wrapper:
  the specs, and the outline's styling, find the blocks as `article > ul`. They
  are capture-phase and stop the event, because CodeMirror would otherwise read
  a dropped file as text and put it in the block. Text has no files, so it is
  left alone. The graph is fetched when a file arrives (`bootGraph()`), so the
  article doesn't suspend on it.
- **`BlobFile` draws a blob block's file** (`Block.blob`) from an object URL,
  made when the bytes are read and revoked when the page moves on.
  `RenderedBlock` draws it above the block's caption, which is the text after
  its first line, and leaves the block's own `##blob` chip out; a block with a
  file keeps its bullet. `getBlob` rejects if this device
  doesn't have the bytes yet, and the page says so with a Try again; they
  arrive from other devices by themselves, but nothing tells the page.
- **The memory backend keeps files in a map by SHA-256**, not the BLAKE3 the
  app uses: nothing outside the page checks, and the browser has no BLAKE3.
  `__quiddityRemote.createBlob` plays another device that has added a file to a
  page whose bytes this one doesn't have, and `kept` lists the hashes kept, for `e2e/files.spec.ts`.
- Playwright's `dispatchEvent("paste", …)` doesn't make a `ClipboardEvent`:
  make one in the page. A `drop` works as it is.

## Routing and boundaries

- **View state is the URL**: `/entity/?id=<main>&open=<a>,<b>` (`lib/nav.ts`).
  A static export can't enumerate entities for path segments, and the right
  pane is a list, not a route.
- **`/` is `Home`, which redirects once the graph has loaded**, at about the
  moment the sidebar's links start working. A link followed first is the
  person's choice, and the redirect, being later, would take over the
  navigation still under way, so `Home` notes links followed before its first
  redirect and stands down. A navigation that isn't a click on a link, such as
  choosing a search result, says so with `noteFollowed`. `e2e/pages.spec.ts` follows the link the moment it
  is drawn, with the destination slow, to hold the race open, and
  `e2e/search.spec.ts` does the same for a search result.
- **The main pane's scroll position is remembered per place** (`ScrollRestore`,
  `lib/scroll-memory.ts`), because `main` scrolls rather than the window, so the
  browser has nothing to restore. A place is `path` and `main`, as in
  `PlaceHistory`. A page that has just been shown is usually too short to
  scroll to where it was, and Next scrolls a `router.replace` route to the top
  after our layout effect, so **the position is put back whenever it moves, until
  the person scrolls** (wheel, touch, pointer or key), the page has been quiet
  for a second, or five have passed. The scroll events in that time aren't
  remembered. A test that scrolls then must use the mouse wheel: a programmatic
  `scrollTop` is undone. **A test must also not let Playwright scroll a link into
  view to click it**, or it moves the pane after its position was read: click
  from the page (`el.click()`), and give the scroll event two frames to be heard.
- **What remembers places (`HistoryKeys`, `ScrollRestore`) starts at module
  load, not at mount.** Both sit in a `Suspense` that waits for the URL, so they
  can mount after a link has been followed; a history or scroll memory begun
  then never saw the place left, and Alt-Left did nothing. Each keeps its state
  at module level, is seeded with where the page was opened (`placeOpened`), and
  `ScrollRestore` hears the pane's scrolling from the first (a capture listener
  on `document`, since `scroll` doesn't bubble). Anything new that remembers
  places must do the same. A test of a race like this passes alone and fails
  about one run in ten under CPU load: use `--repeat-each` with busy loops
  running.
- Reading the URL suspends, so each pane, and each secondary within the right
  pane, has its own `Suspense` and error boundary (`Region`): a slow or broken
  one holds up nothing else. A card's header sits outside its content's
  boundary so it can always be closed.
- **The graph only exists in the browser**, so everything that reads it (the
  page, and both sidebars) renders inside `ClientOnly` and isn't prerendered.
  Each route wraps its page in `ClientPage`; the layout doesn't, because the
  published build's `/page/[name]` is drawn at export time instead.
  `bootGraph` loads the snapshot from disk there (`lib/prerender.ts`, which
  fetches `node:fs` with `process.getBuiltinModule`: Turbopack refuses to
  bundle it for the browser), and `useView` reads no query string until
  hydrated, since `useSearchParams` would make the export give up on the page.
  A static export never renders them on a server, but **`next dev` does, on
  every request**: a pane left outside `ClientOnly` works in the export and
  fails in development with a server error. The `e2e-dev` tests exist for
  this.

## Editing

- **`EditableOutline` provides an `Editing` context** (which block is being
  edited, where the caret goes, the entity's blocks in reading order); an
  `Outline` outside one, such as in references, is read-only.
- **`BlockEditor` is a CodeMirror editor bound to one block.** What is typed
  goes in as the splice that was typed, last change first so offsets stay
  valid; changes from the graph come back as the smallest edit, marked
  `fromGraph` so they aren't sent again. **It reconciles against
  `graph.blockText`, never against props**, which can be a keystroke behind.
- **Keys act on the graph, then say where editing continues.** Moving blocks
  makes React remount them, so a key that moves the block being edited calls
  `edit(id, caret)` *before* the structural change so the new editor opens at
  the right place. Undo and redo are the graph's (`Mod-z` in the editor, and
  `UndoKeys` when no editor is focused); there is no editor-level history.
- **Selecting blocks** (`lib/block-selection.ts`, `selectionHandlers` in
  `editing.tsx`) is separate from CodeMirror's selection of text. Its listeners
  are on the `document`, in the capture phase, since an editor would take
  Select All for its text and a drag starts in one block and ends in another.
  **The first Mod-a in an editor is still the editor's**; with its text all
  selected (or none) the next makes a block selection and closes the editor.
  Rows carry `data-block-id` and `data-outline` (the `Editing.scope`), so
  an outline at the side doesn't answer for the main one. **A drag finds its
  block by height, not by what is under the pointer**, so a gap, the margin
  or the far side of the page doesn't lose it, and it swallows the click that
  follows its release, which would edit the block. What is selected is
  filtered by the blocks still there. **Tab and Shift-Tab act on a selection**
  through `graph.indentBlocks`/`outdentBlocks`, which are one undo step in
  Rust and treat a block chosen with its parent as the parent's. **So do the
  move keys** (`lib/move-keys.ts`: Cmd-Shift-arrow on a Mac, Alt-Shift elsewhere):
  an editor has them in its own keymap, so its caret is kept, and the
  page-level handler leaves editors alone and moves the selection or, with none,
  the focused block, putting the focus back since the row can be remounted.
  Backspace and Delete delete a selection (`graph.deleteBlocks`, one undo
  step) and clear it, since the blocks are gone. **Copy, cut and paste are the
  browser's `copy`/`cut`/`paste` events**, not keys, so the clipboard is
  written inside the gesture and the menus work; they leave inputs and editors
  alone. The clipboard holds the outline text from `graph.copyBlocks`; a paste
  goes after the last selected block that isn't inside another
  (`lastSelected`) or after the block with the focus, and selects what it made.
  A test plays a paste with a `ClipboardEvent` at `document.activeElement`.
  **`EditableOutline` has a polite live region** (`role="status"`, `sr-only`, under
  the outline) that `Editing.announce` writes to; the selection's own count is
  said after 300 ms of no change, and not at all if an action has just
  announced itself (`lastAction`), so a paste isn't followed by "3 blocks
  selected". An identical message is made different by a trailing non-breaking
  space that comes and goes, or a screen reader says it once. Tests read it as
  `main [role=status][aria-live=polite]`.
  **An editor's own paste handler** (`block-editor.tsx`) asks
  `graph.classifyPaste` what the text is: plain text is left to CodeMirror, one
  bullet is inserted as its text, and an outline goes to
  `graph.pasteIntoBlock` (after the block, or in place of it if it is empty),
  with editing continuing at the end of the last block made.
- **`EditToolbar` is drawn only with an on-screen keyboard** (`useKeyboardInset`,
  from the visual viewport: 100px or more of the window uncovered by it), in a
  portal fixed `bottom: inset`. Its buttons stop `pointerdown` and `mousedown`
  so the editor keeps focus, and find the editor from `document.activeElement`.
  **Indent, outdent and move are `blockCommands`, shared with the keys**, not
  copied. `e2e/keyboard-toolbar.spec.ts` plays a keyboard by shrinking
  `visualViewport.height` and firing `resize`. **It reserves space under itself**:
  it sets `--edit-toolbar-space` (keyboard plus bar) on the root, which
  `main` takes as padding and scroll padding. The viewport asks for
  `interactive-widget=resizes-visual` so the keyboard is a visual-viewport
  matter in every browser; a webview that resizes the layout instead would
  never show the bar.
- Removing a focused editor fires a blur that isn't the user leaving, so
  `closing` is set in a layout effect (which runs before the DOM goes).
- IDs held by editing state go dead across an undo of a deletion; that just
  ends the edit.

- **Leaving a block saves it** (`EditableOutline`): it remembers each block's
  text from when editing began and calls `graph.commitBlock(id, before)` when
  editing moves on or the page is left. That makes an entity only for a link
  with qualifiers that the edit added. A link to a name nobody has made is an
  ordinary link to a virtual entity (`~name`), which looks like an empty one
  and is made by writing to it (the empty outline's "add a block" does, via
  `createBlock`). A qualified link with no entity yet is `NewEntityLink`, an
  `<a href="#">` drawn like any other, and following it makes the entity
  (`graph.followLink`).
- **Links are completed in the editor** (`lib/link-completion.ts`, with
  `lib/auto-brackets.ts` pairing `[`). **The search is not part of the
  keystroke**: a plugin runs it a frame later, for what is typed by then, and
  the list keeps its last answer until it lands. Down and Up (`find`) search
  first if it hasn't, so they never choose from an answer to older text. It
  leaves out a link to nowhere whose name is the text being typed: the block's
  text is in the graph by then, so the half-written link would offer itself.
  Its keys sit above the outliner's, so
  in a link the arrows and Enter are the list's; **Escape is left to the
  outliner** unless an entry is chosen, or leaving the block would no longer
  save it. The list opens only on a user edit that touches the link (never a
  `fromGraph` change, never just the caret arriving), and choosing an entry
  writes it into the link, marked `previewing` so it doesn't reopen the list.
  Enter with no list follows the link. A hit's `link` is the text to write,
  escaped and qualified by Rust.
- **A line property is text, not a chip** (`PropertyLine`, as in Logseq): `key::`
  in bold, then the value, whose links are links. **Its key goes to the entity
  that defines the property** (`Property.definition`). With none yet it is a
  button, and following it makes the entity (`graph.defineProperty`), as a link
  to nowhere does. **A
  tag's chip (`inline`) goes to the entity it names** instead, and with none
  makes it as a link does (`graph.followLink`): a tag is a link, not a property. A block
  of nothing but properties has its bullet hidden, not removed, so the lines
  line up with the text around them.
- **An entity's properties block** (`Block.propertiesBlock`, from Rust) is
  drawn on `bg-surface-properties` with `data-properties-block`, and
  `EditableOutline` offers `AddProperties` (an empty first block) while there
  is none, and remembers the block it made (`offered`): leaving it with no text
  deletes it (`graph.dropEmptyFirstBlock`, one undo step of its own). Any other
  empty first block is left alone.
  **Completion in it is `@codemirror/autocomplete`** (`lib/property-completion.ts`):
  keys at the start of a line and a key's values after `::`, from
  `graph.propertyKeys` and `propertyValues`, which are Rust (`completion.rs`) and
  not cached. The source is `Prec.highest` before the outliner's keys so Enter
  chooses an entry, with `interactionDelay: 0`: the default ignores keys for
  75 ms after the list opens, and a quick Enter would then split the block.
  **Enter in a properties block adds a line** (the outliner's Enter would split
  the block), except on an empty last line, which is removed as the body's
  first block is made after it.
  It offers nothing unless the block is a properties block or the one the offer
  made (`BlockEditor`'s `properties`, read through a ref so a block that becomes
  one is completed). The list takes the page's colours from tokens.
- **Meta-properties** (`meta-sections.tsx`): flags with no chip go under the
  title, and Inherited and the inverse trees go below the body. A line with
  `flags` is ringed and carries `data-flagged`, with the reasons as its
  title. All the words come from Rust.
- The main pane's title (`EditableTitle`) renames in place when the entity
  is `renamable`: Enter or leaving the field keeps it, Escape drops it. Side
  cards and the journals feed show plain titles.

## Graph view

`/graph/` (an entrypoint) draws `graph.connections()` with d3: `d3-force` lays
it out, `d3-zoom` pans and zooms, `d3-drag` moves nodes. **It is drawn on a
`<canvas>`**: an element per node and edge moved on every tick was slow. **d3
owns the canvas and a `sr-only` list beside it; React owns the elements and
calls `draw()` once on mount and `update(data)` when the graph changes.**

- **Painting** is one function, `paint`, reading the nodes, links and view as
  they are; anything that changes them asks `repaint()`, which coalesces to one
  paint per animation frame and does nothing while the page is hidden. Colours
  are the theme's (`--graph-link`, `--graph-node`, `--graph-node-stroke`, `--graph-label`), read
  from the stylesheet because a canvas can't take them from a class, and read again
  when `prefers-color-scheme` changes. The
  backing store is scaled by `devicePixelRatio`, and **everything is sized in
  CSS pixels**: the canvas transform is `ratio·k`, so a retina display gets
  sharper output, not bigger nodes. The ratio is re-read when the canvas
  resizes and when a `(resolution: …dppx)` query stops matching (moving
  between screens, browser zoom).
- **Sizes live in `lib/graph-style.ts`.** Node radii are in graph space and
  scale with the zoom (`max(3, 3·ln(degree+1))`); **text and line widths are
  held at a size on screen** by dividing the zoom out (`1 / view.k`), so a
  label is 10px whatever the zoom. Don't put a font size or line width in
  graph units.
- **Hit-testing is ours** (`nodeAt`): the nearest node within its radius, in
  the canvas's pixels. The zoom's `filter` refuses a press on a node so the
  drag gets it, `d3-drag`'s `subject` is `nodeAt`, and hover, click, Alt-click
  and double-click on the background all use it. **A press starts a drag, but
  nothing is disturbed until the pointer moves**, or a click would stir the
  layout.
  **`d3-drag` reports a drag in the subject's coordinates**, so the subject is
  where the node is in canvas pixels (not in graph space), or a grabbed node
  jumps by the view's offset.
- **The accessible graph is the list of real `<a href>` links** (click opens
  the entity, shift-click opens it at the side; focus highlights the node on the
  canvas), and the canvas is `aria-hidden`. They are not positioned, which is
  what makes them free. They carry `data-x`/`data-y` only when the layout is
  still, and the canvas carries `data-view` and `data-settled`: tests read
  those (and `data-grabbed`, where a drag has the node, in canvas pixels), and
  click the canvas where the node is. Don't rely on them elsewhere.

- **Positions and the view are remembered** (`lib/graph-layout.ts`, in memory
  and in localStorage), so leaving and coming back finds everything where it
  was. They are saved when the layout settles, after a zoom and on leaving, and
  **nothing is saved before the first nodes are drawn**: setting the initial
  zoom ends a zoom, which would otherwise wipe the layout about to be
  restored. Entities with no position are placed beside one they link to.
  **Entities that have a position are held (`fx`/`fy`) while the new ones find
  theirs, then let go when the layout ends**: otherwise the link force pulls a
  settled layout towards its rest length on every load. With nothing new the
  simulation is stopped (d3 starts one running, at full heat, as it's made). Entities placed by an unfinished run stay free
  across a second `update`. Positions of entities that have gone are dropped
  when next saved.
- Dragging lets every node go at the start, so the rest untangles around the
  dragged one, and the dragged node on release (nodes aren't pinned).
- Link strength is d3's default (1 over the fewer links of the two ends), so a
  link between hubs is slack. Don't set a flat strength.
- **Framing** (`lib/graph-fit.ts`): with no remembered view the graph is framed
  once at the first draw and again, animated, when the layout settles, until
  the person pans or zooms (`tracking`). It frames the largest connected group
  (every entity when nothing is linked), so loose entities don't shrink the
  view. **Reset view** and a double-click on the background do the same.
  Alt-click frames a node and its neighbours instead of opening it. The animation is
  `d3-transition`, imported for its effect on selections (it works on a canvas
  selection as on any other); a pan or zoom by the person interrupts it.
- **Options** (`lib/graph-filter.ts`): a panel, closed when the page opens, with a checkbox each for property links
  (the `weak` edges), journal pages (`Connections.nodes[].journal`, from Rust),
  empty leaf pages (`nodes[].empty`: no words outside the title and properties
  block, one link, which comes in) and orphan pages, all off to begin with,
  which `Canvas` applies to the data before `update`. **Leaves and orphans are
  judged after journals and property links are hidden**, so hiding either also
  hides what only they linked. Leaves go before orphans and aren't looked for
  again, so a hidden leaf can leave its neighbour an orphan. A test opens the
  panel first (`showOptions`); `e2e/graph-filter.spec.ts` tests the filter in
  Node. The canvas carries `data-links` and
  `data-weak`, how many links there are and how many are weak, and `data-drawn`,
  how many the last paint stroked (fewer if the simulation was never given the
  links, which `update` must always do), for tests.
  **`update` always gives the simulation its nodes and links**, placing
  anything or not: the link force is what turns a link's ends from IDs into
  nodes, and `paint` skips a link that still has IDs. So those two counts are of
  the links whose ends were found, which is what lets a test notice one that
  wasn't. Choices
  aren't remembered, and a hidden node's position is forgotten when next saved.
- Labels are not drawn when a node is under `LABEL_DIAMETER` (10px) across
  on screen, except for the node hovered or focused. The canvas carries
  `data-labels`, how many the last paint drew, for tests.

## Disambiguation

`/disambiguate/?link=<key>` (`components/disambiguation.tsx`) lists the entities
an ambiguous link matches, each with its title and its read-only properties
block. **The link is in the URL as `View.link`**, so `viewHref` keeps it when a
side card is opened. An ambiguous `LinkOrNot` and Enter in the editor go there;
`graph.linkMatches` is the cached read.

## Search

The action strip above the main pane holds the search button; **Cmd/Ctrl-K**
(captured, so a focused editor can't take it) opens the panel
(`components/search.tsx`).

- **A panel is a list of `Facet`s** (`lib/search/facet.ts`), one section each,
  in order. A facet is `search(query, graph) => Hit[] | Promise<Hit[]>`, best
  first. `useSearch` runs them independently and keeps each one's latest
  answer, so a slow facet (full text, embeddings) never holds up a fast one
  and an old answer stays until its replacement arrives. **It searches for the
  deferred query** (`useDeferredValue`), each facet in a task of its own that
  a newer query cancels before it starts: the replica is in this thread, so
  the saving is the work never begun.
- **Make new facets by composing**: `limited(n, facet)`, `when(applies, facet)`
  (a prefix such as `>` that selects actions, say). A hit's `target` is data
  (`entity`, or `run`), not a callback, so hits can be ranked and logged later.
- **Matching lives in Rust** (`quiddity-view`'s `search.rs`, where it is
  mutation-tested), reached through `graph.searchTitles`. Facets only shape
  its answers into hits.
- **The Text facet** (`search_text`) is BM25 over every block: all the words
  must be there and the last may be unfinished, so `note` finds `notes` while
  `not loro` doesn't. It shows the stretch of the block around the first match.
  An entity's own name belongs to the Pages facet, not this one.
- The graph's `searchTitles` and `searchText` aren't cached: the panel asks per keystroke and
  an answer is rarely wanted twice.

## All entities

`AllEntities` is a sortable table with a checkbox on each row, above a title
filter and a "Hide journals" checkbox (ticked to begin with; the rows say
`journal`, from Rust). It makes no entities: the tests make one by linking to
it from a journal block. The filter is read as `useDeferredValue`, and the
filtered and sorted rows are `useMemo`ed, so typing in the box isn't held up
by thousands of rows. **Selection is the set of IDs ticked, filtered by the
rows still there and shown**, so an entity that an undo or a sync removes, or
that the filter hides, simply stops counting. Deleting asks first, inline
(`role="alertdialog"`) rather than with `window.confirm`, which the Tauri
webview can't be relied on to show; **changing the selection withdraws the
question**, so what is confirmed is what was asked about. Deletion
(`graph.deleteEntities`) is one undo step, and links to a deleted entity stay
in the text as links to a virtual entity.

## Rendering

`RenderedBlock` is how a block reads when not being edited: `splitBlock` takes
line properties out for chips and swaps inline ones for placeholder characters,
`remarkQuiddity` turns `[[links]]`, `((refs))` and the placeholders into custom
elements (in text only, so never in code), and `react-markdown` draws the rest.
Block text comes from other devices and is untrusted, so:

- **Don't add `rehype-raw` or render HTML strings.** Raw HTML shows as text.
- Only `http(s)` and `mailto` links are links, opened through
  `lib/open-external.ts`; anything else is inert text.
- **Images aren't fetched**: a remote image is a request to its author.

## Link hints

`LinkStatus` (in the root layout) is the toast in the bottom-left corner
(`data-link-status`) that names a link's destination, from the one-value store
in `lib/link-hint.ts` (`docs/Link hints.md`).

- **A link sets it when entered or focused and clears it when left**:
  `useLinkHint(() => text)` gives the handlers, and clears the toast if the link
  unmounts while it is showing, but only if it is still that link's own text.
  `EntityLink` does the same by hand, since it also owns the preview.
- **`EntityLink` reads the entity's title when entered** (`graph.entity`, which
  can fail for a link to a deleted entity, so it is guarded), so whoever draws the
  link gets the name without passing it. A link to the web shows its URL;
  `ExternalLink` in `rendered-block.tsx`. A link to an app page shows its
  entrypoint title (`appPageTitle`), as `AppLink` there.
- **The preview is a sibling of the link, not a child**, or its links would be
  nested anchors. It is `inert`, `pointer-events-none` and `role="tooltip"`, appears
  after `PREVIEW_DELAY_MS` and only if there is a properties block, and Escape
  dismisses it. The link's `title` is left off while it shows.

## Tests

Playwright (`pnpm ui build`, then `pnpm ui test:e2e`). Most tests (`e2e`)
run against the static export; a few (`e2e-dev`) run against `next dev`, which
renders on a server as the app does in development, and also shows React
warnings that a production build hides (duplicate keys, say), which the page
logging them fails the test. Each test starts from the same made-up graph. `e2e/fixtures.ts` fails a test
if the page logs an error. Pitfalls:

- The sidebar repeats names (Favourites, Recents), so scope a link locator to
  `main` before `.first()`.
- On the in-memory graph a page reload starts over, so a test that has changed
  something must move by clicking (the sidebar), not `page.goto`.
- A block's rendered text is `[data-block-text]` and an editor is `.cm-content`.
- The page links an icon (`app/icon.svg`, a copy of the app icon's master), so
  Playwright's full Chromium doesn't ask for `/favicon.ico`, whose 404 would
  fail every test. Keep the link: without it, full Chromium needs an empty
  `favicon.ico` in `out/` and `public/` for the run.
- `e2e/debounce.spec.ts` and `e2e/share.spec.ts` test `lib/` modules in Node
  and use no page.
- Typing `\n` presses Enter, which splits the block; use Shift-Enter for a
  newline. Press `Control+Shift+Z`, not `Control+Shift+z`: Playwright otherwise
  sends a lowercase `z` that no keyboard does.
