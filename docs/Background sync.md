- Syncing while the app isn't open, which on a phone means being woken by the system for a few minutes at a time. Built for Android; **none of the Android side has been run on a device yet**, only compiled by CI. [[Background]]
- What it is for
	- Finishing a sync that is under way when the user leaves the app, and an occasional sync of a phone that hasn't been opened, so that it isn't far behind when it is. The phone is not a peer that others can count on reaching: the always-on devices are the desktops. [[App sync]]
- The parts, in the order they were built
	- `Peer::settled(timeout)` waits until the device is alone, synced or present, or the time is up, and says which. It settles when *any* listed device is connected and has nothing this one lacks, not every device, since most are asleep. [[Sync status]]
	- The shell's live session is kept for the life of the process, so that a background run and the app share one graph and one endpoint. [[The shell]]
	- `background::sync_once` opens the graph if no window has, waits for `settled`, saves, and stops the network gracefully. It never makes a graph, and if a window opens during a run, the run leaves the network to it. `sync_in` finds the graph as the app's startup does, from the data directory.
	- The Android plugin (`apps/app/plugins/background-sync`, a Tauri plugin that is its Kotlin) and the JNI calls it makes into the library (`apps/app/src-tauri/src/android.rs`).
- On Android
	- **Periodic**: a WorkManager job (`SyncScheduler`, `SyncWorker`) every six hours, on any connected network, scheduled when the app starts. It syncs once for up to two minutes. On a metered network it syncs the graph and not the files ([[Blob transfer]]), since the files can be large. Reaching nobody is not a failure; only a run that broke is retried, up to three times.
	- **Holding**: when the user leaves the app (`onPause`) with a sync outstanding, meaning the live session is behind, a foreground service of type `dataSync` (`SyncHoldService`) keeps the process for it, with a notification, until nothing is outstanding or a minute has passed. It is a way to finish what had started and never a reason to stay connected.
	- The Kotlin and Rust meet at `Native` and `android.rs`, whose names must agree (`Java_uk_co_aylett_quiddity_sync_Native_*`), and at the outcome numbers in `Native.kt`, which a Rust test pins. A background run has no Tauri to ask where the files are, so it works out where Tauri keeps them (`background::android_dir`: the data directory, then the identifier), and the app warns at startup if Tauri says otherwise. A wrong place finds no graph and never makes one.
- Things to know
	- A run in a process with no window installs no JNI context for iroh's DNS, which iroh allows (it uses its own nameservers). Installing one would panic the app if its window then started, since the window's glue installs one too.
	- `unsafe_code` is denied in the app crate and allowed in `android.rs` alone, because JNI exports are `no_mangle`. The workspace forbids it; the app crate has its own copy of the lint tables to change that one line, and they must be kept in step.
	- The plugin's dependency versions are locked (`android/gradle.lockfile`, from `dependencyLocking` in its `build.gradle.kts`), so that the build can't move under us, and SonarCloud asks for it (`text:S8569`). Only this module is locked: the project around it is generated by the Tauri CLI and isn't ours. CI writes the locks again and fails if they differ, so after changing a dependency, or when the Tauri CLI moves the generated project's plugins on, refresh the file from `src-tauri/gen/android` with `./gradlew :tauri-plugin-background-sync:dependencies --write-locks` and commit it. The usual `failOnNonReproducibleResolution()` is left out because Gradle refuses it beside locking.
	- `android.rs` is compiled by the tests on every platform, so a change that breaks it fails there, but it needs a JVM to run, so it is a shim and the logic it calls (`background.rs`) is what is tested. CI's mutation run covers the default workspace members, which leave the app out, so none of this is mutation-tested; `cargo mutants -p quiddity-app` would do it.
	- The Kotlin is tested on the JVM with Robolectric, with a fake in place of the library: `Sync.backend` is the seam (`SyncBackend`, which `NativeBackend` implements by calling `Native`, the only class that loads the library), and the decisions that have no Android in them are `SyncPolicy` and `HoldWatcher`, which take the clock and the sleep as parameters so that no test waits. The tests are in `android/src/test`.
	- CI builds it and tests it: the `android` job builds the app for one ABI, which compiles the Kotlin and links the JNI calls, then runs the plugin's tests in the generated project and writes a JaCoCo report, which the `sonarcloud` job reads (SonarCloud can't measure Kotlin coverage any other way). Nothing runs the real library on a device. [[Testing]]
- Limits that are the platform's
	- Doze and App Standby batch background work, so "every six hours" is roughly, and a desktop is only reached if it is awake at the same time. The graph is complete on every device, so being late costs freshness and nothing else.
	- A periodic job runs for about ten minutes at most. A `dataSync` foreground service is limited to a few hours a day on Android 15; a minute at a time is far inside that.
	- The notification needs the notification permission to show on Android 13 and later. The service runs without it, unseen, and the app doesn't ask for it.
	- iOS is not planned yet.
- To find out on a device
	- The log (`adb logcat -s QuiddityBackgroundSync`) says what each run did. Running one now: `adb shell cmd jobscheduler run -f uk.co.aylett.quiddity <job id>`, or `adb shell dumpsys jobscheduler` to find it. Leaving the app mid-sync should show the notification.
