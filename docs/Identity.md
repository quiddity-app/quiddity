alias:: [device key, device ID, graph ID, node ID, identifiers]

- Planned, not built. How a replica, a device and a graph are told apart, and how the secret one is kept from being misused. Today a device is its [[iroh]] key and nothing else, and the [[Loro]] peer ID is chosen at random each time a replica starts. [[Design]]
- Built so far: the types, their written form and the derivations, in [[quiddity-identity]]; and the graph ID, made with each new graph and kept in its document. The sync handshake checks it; the device key is kept apart from the graphs and a new graph's endpoint key is derived from it. node IDs are kept for the replicas that are kept, sealed so that they open only on the device that made them. What notices a copy is not built; the steps at the end say what comes next.
- What there is now
	- Two secrets, and only one of them in use for any graph. Both are 32 bytes. [[Storage]] [[Sync]]
		- **The device key**, in `device.key` in the device's own configuration directory (`~/.config/quiddity` on Linux; the app's own on a desktop; `--config-dir` or `QUIDDITY_CONFIG_DIR` says otherwise), written as a `qdk_` token. It is a seed that nothing signs or encrypts with directly, so neither asymmetric nor symmetric: it is key material.
		- **The endpoint key**, an Ed25519 secret key, so asymmetric. Its public half is the endpoint ID, which the UI, the CLI and the graph's [[Device list]] call the device ID. A graph made now derives it from the device key and the salt in its file, and never stores it. A graph made before keeps its own in its file (the `endpoint_key` table of `graph.quiddity`), so that its device ID doesn't change.
	- Nothing else is a key. Sync, [[Blob transfer]] and [[Presence]] all use the endpoint. The updater's signing key belongs to releases and is not in the app. [[Updates]]
	- Device IDs are per graph, because each graph's endpoint key is its own. A graph made now can be copied to another device without taking the device with it: the other device's key derives another endpoint key. A graph made before still carries its endpoint key in its file, so copying it copies the device. And a copy made beside the original, on one device, is still the same device: that is what [[Copied graphs]] is for.
	- The node ID, Loro's peer ID (a 64-bit number), is kept for the replicas that are kept: the shell's and the headless node's, in the graph's file, sealed. Loro chooses one at random for any other replica, so every launch of the UI's replica still adds a peer to the graph's version. [[App sync]]
	- The hello carries the graph's ID and refuses another's, so two graphs that have IDs are never merged. A graph from before graphs had IDs has none, and is accepted by any peer until it is given one. [[Sync]]
- Four identifiers, each its own type
	- **Device key**: the one secret, made once per device and never used directly. It is a seed, not a signing key: nothing signs with it or encrypts with it, so it cannot be used for the wrong thing. Everything else is derived from it.
	- **Graph ID**: 128 bits, random (a version 4 UUID), made when the graph is created and kept in the graph's document, so every replica has it. It is not secret.
		- Only creating a graph makes one, in its first edit. A blank replica has none until it imports the first update, so two devices can't each invent one and then have to agree.
		- A graph made before this has none, and keeps working: a graph with no ID is accepted by any peer, as a blank replica is. Nothing gives it one by itself, since two devices that each did would make two, and one would lose. `quiddity-node identify` does it, on the one device, and prints the ID; it syncs like any edit. It refuses a blank replica, and a graph with an ID, or with something where one should be that this build can't read.
		- The hello carries it. A replica refuses a peer with a different one, so unrelated graphs never merge.
		- It names the graph in the [[Copied graphs]] map.
		- A blank replica is the one exception to the refusal, and only when it is joining on purpose. Pairing shows the graph's name and ID on both devices before anything is taken, so that nobody joins whatever graph a pasted device ID happens to lead to.
		- The refusal also stops device lists merging: today two unrelated graphs that both hold full history in memory pass the hello and union their blocks and their device lists, so each graph's devices become trusted by the other. (quiddity-app/quiddity#290)
		- UI state that belongs to one graph, such as recents, is keyed by it. Today it is keyed by entity ID and title alone.
		- An export carries the graph ID, and importing it into the same graph keeps it. An import that makes a new graph gets a new ID, so a rebuilt graph can't be mistaken for the original or for a stranger. Which of the two an import is has to be asked, not guessed. (quiddity-app/quiddity#288)
	- **Device ID**: the public half of the key a device uses on the network. It is what the device list holds and what a person pastes to [[Add a device]]. It reveals nothing else about the device.
	- **Node ID**: the Loro peer ID. A node is one replica, so a device holds several: the shell's, and the UI's. Loro cannot tell two replicas apart that share one, and two histories under one ID is corruption, so a node ID is never reused by two replicas that might both edit.
		- It is random, not derived: deriving it would give the same ID to a copy.
		- The store keeps it in the graph's file, sealed. A file made on another device doesn't open with this device's mask, so the replica there knows it is a new one and makes a node ID of its own, which it keeps. What the first device wrote stays under its own.
		- It is applied when the graph is loaded, and a graph that is made is made as that node, so a graph isn't left with one more peer, never heard from again, for each time it was made or opened.
		- Setting one that already has edits carries on after them: that is what keeps a replica one node, and what makes restoring one from a copy that is behind dangerous. [[Copied graphs]]
		- Each device records in the graph the node IDs it has used, beside its stored version, so that anyone can say which device made a change. Not built.
- Deriving what is used from the device key
	- The device key is the input to a key derivation ([[BLAKE3]]'s `derive_key`), with a context string for each use and a salt, so that one use can never be passed off as another.
	- **The salt is random, made with each graph's file and kept in it. It is not the graph ID**, which is what this page first said: a blank replica has to give out its device ID, to be let in, before it has met the graph and learned its ID.
	- **Endpoint key**: an Ed25519 key per graph file, derived. It is what iroh is bound to, and what makes a device ID per graph, as now, but without keeping a key in each graph's file. One device key backs up every graph, and a device's IDs in two graphs can't be linked.
	- **Node mask**: 64 bits, derived the same way. A node ID is stored XORed with it, together with a check of the plain value, so that it is only readable on the device that made it. Read on another, the check fails and the replica knows it was copied. The mask is not secrecy: a copy that takes the device key too is the same device. It is there to tell, not to prevent.
	- Existing graphs keep their endpoint key (converted from `device.key` in the graph's directory when the file is first opened, and since then kept in the file), so that device IDs already in other devices' lists stay valid. They are given a salt when they are opened, for what is yet to come, and never ask for the device key. Moving them to derived keys would change the ID, so it is a re-pairing and is not forced.
- Keeping a key from being misused
	- Each identifier is its own type, and none converts to another. A secret has no `Display`, no `Serialize` and a `Debug` that prints nothing; it is wiped when dropped and can't be cloned by accident. There is one function that turns it into its stored form, in the module that writes keys, and one that reads it.
	- It is kept in the device's own configuration directory, not in a graph's and so not copied with one, with mode 0600, or in the platform's keychain where there is one. It is never put in a graph, an export, a log, a URL, a pairing ticket, an argument on the command line (visible to every process) or anything the UI is sent. The UI only ever has public IDs.
	- Parsing says what was found: a device ID where a key was wanted is an error that names both, rather than "bad length".
- How they are written down: GitHub's token format, so a leaked secret can be found. [[Secret scanning]]
	- `qdk_` then the payload in base62 at a fixed width (43 characters for a key), then a six-character checksum: the CRC-32 of the payload, in base62. A token has exactly one spelling. Text that begins `qdk_` and does not checksum is a typo, or not ours, and is refused without trying it. A scanner can check the same way and so skip what only looks like a key.
	- The only secret persisted or shown to a person is a `qdk_` key. A derived key is never stored: it is worked out each time.
	- Public identifiers have a prefix of their own and the same checksum, so a pasted device ID is checked for typos and never matches a scanner's pattern for a key: `qdi_` for a device ID, `qgi_` for a graph ID and `qni_` for a node ID. Bare endpoint IDs, as printed now, are still accepted.
	- The prefix also names the format's version, so that a change to the payload is a new prefix and not a guess.
	- Getting it picked up on GitHub is a separate step: it supports patterns for its own users, and for others through its partner programme. Whatever the requirements are when the format is ready, the prefix and the checksum are what they ask of a token.
- Steps, a stack of changes each of which builds and passes on its own
	- Built: the types, the written form and the derivations. [[quiddity-identity]]
	- Built: the graph ID, made with the graph and kept in its document. [[quiddity-core]]
	- Built: the hello carries it, and a session refuses another graph's. The sync protocol changed, so its ALPN name did (`quiddity/sync/3`). [[quiddity-sync]]
	- Built: the device key is in the device's own configuration directory, and new graphs' endpoint keys are derived from it and a salt in the graph's file. A file of the old layout gains a salt. [[quiddity-node]]
	- Built: node IDs, stored sealed with the mask (storage layout 3) and set as Loro's peer ID when the graph is loaded. [[quiddity-node]] [[quiddity-core]]
	- Planned: the map of nodes to places, and forking a copy. [[Copied graphs]]
	- Planned: noticing a twin, from changes that arrive under this replica's own node ID.
	- Not in the stack: recording node IDs in the device list, the UI replica's own stable node ID, showing the graph's ID when pairing, and writing device IDs with the `qdi_` prefix in the UI.
- Open questions
	- How many nodes the UI has. Two windows on one graph would need an ID each: leased from the shell, and given back when the window closes.
	- Whether the device list should be keyed by the device ID or by the node ID. It is by device ID now, which is what authorisation needs; compaction counts versions by peer, which is the node ID.
	- What a person does when they lose the device key. The graph is still on their other devices, so the answer is probably to add the new device as a new one. Nothing revokes the old one yet. [[Device list]]
