- What a device keeps on disk, and what it works out again.
- The [[Loro]] document is the only source of truth.
	- Text is stored in Unicode NFC. [[Unicode normalisation]]
	- A graph on disk is a directory, made by `quiddity-node init`. The graph is one [[SQLite]] file in it, `graph.quiddity`, holding the graph's snapshot and a random salt, and, for a graph made before the device's key was kept apart, its endpoint key. [[quiddity-node]]
		- Blobs and `unreferenced-blobs.txt` are still beside it, for now. Planned: they join the file, so that a graph is one file to copy. A graph's old `blobs/` directory can already be moved into the file: it is read, every blob in it is kept in the file, and it is set aside as `blobs.migrated/`, not deleted. Nothing does that yet; the change that makes the file hold the blobs will.
		- The file's `blob` table and the store that serves it to [[iroh-blobs]] are built and tested (`blob_store`), but nothing uses them yet. It is layout 2, and a file of layout 1 gains the table when opened.
		- A blob is kept whole. One being fetched from another device is kept in memory, grown by verified data and never by a size the peer claims, until it is whole, so a crash loses it and it is fetched again. A file over 1 GB is refused: that is SQLite's limit on one value.
		- A directory from before, with `graph.loro`, `graph.loro.bak` and `device.key`, is converted the first time it is opened, and those files are kept with `.migrated` added to their names, and the backup becomes the previous generation. Delete them once the graph opens. The key is in `device.key.migrated`.
	- Saving writes the whole snapshot in one transaction that is flushed to disk before it counts as done, so a crash, even a power loss, leaves the previous snapshot. The one it replaces is kept as the previous generation, and loading falls back to that if the current one can't be decoded, and the app shows a [[Recovery]] screen if that fails too. Saves are serialised. A save records this device in the graph's device list, and compacts what it writes. What it records is what the snapshot held *before* this save, never what it is about to write: other devices act on the record at once, by dropping history up to it, so a write that then failed would have left them ahead of this device. The record lags one save; the history kept doesn't. [[Compaction]]
	- The file is one file at rest: it uses a rollback journal rather than write-ahead logging, so there is no `-wal` or `-shm` beside it. A second process that opens it waits a few seconds and then reports that it is busy.
	- **The device's key is not in the file**: it is in `device.key` in the device's configuration directory, one for all its graphs. A new graph's endpoint key is derived from it and the file's salt each time it is wanted, and stored nowhere. So a graph's file taken to another device is another device there, and a graph can be shared without sharing the device. [[Identity]]
	- A graph made before has its endpoint key in its file, so such a file is still a secret: it is created readable by its owner only, and must not be published or shared as it is. `quiddity-node snapshot FILE` writes the snapshot alone, which is what [[Static build]] publishes. Copying such a file copies the device. A copy beside the original on the same device is the same device in either case, which [[Copied graphs]] is designed to notice and is not built.
	- The file's layout is version 4: the snapshot, the endpoint key (a graph made before has one), the blobs (layout 2), the salt (layout 3), and this replica's node ID, sealed. A file of an earlier layout is converted when it is opened, after checking that it is exactly that layout and under a write lock, so that two processes opening it agree: layout 1 gains the blob table, the salt and a place for the node ID, layout 2 the salt and the place, and layout 3 the place. The node ID itself is made when it is first wanted. A build from before refuses a layout it doesn't know.
	- Starting again after a graph can't be opened sets the whole file aside as `graph.quiddity.damaged-<time>`, every byte of it, and makes a new one. The salt, and the endpoint key of a graph that has its own, are carried over if the damaged file is readable enough to give them up, so the device keeps its identity; if not, the device gets a new one. A file with a key and no graph is a device that has no graph yet. [[Recovery]]
	- The file is treated as untrusted, because a graph may be copied from somewhere else. [[SQLite]]
		- It must carry Quiddity's `application_id` and a layout version this build knows, and its schema must be exactly ours: a trigger, view or table we didn't make refuses it.
		- Connections run in SQLite's defensive mode, with triggers, views and schema-defined functions turned off. Loading also runs `quick_check`.
	- [[The shell]] keeps its graph the same way, in the app's data directory, or wherever `QUIDDITY_GRAPH` says. It saves after each batch of updates from the UI.
- Blobs, the bytes of [[Binaries]], are kept by hash in `blobs/` beside the graph's file, in an [[iroh-blobs]] store. They are not derived and not in the document. `unreferenced-blobs.txt` beside them is the node's record of when it first saw each file that nothing refers to, for deleting them.
- Everything else is derived.
	- The index, of names and aliases, properties, links and how each resolved, is rebuilt from the document in memory and never synced or stored. [[quiddity-core]]
	- Full-text search reads every block when asked, from the text the view keeps. [[Text search]]
	- What costs time at start and after an edit, and what is planned about it. [[Performance]]
- Planned, not built
	- A map of where the device's graphs are, which is what notices a copy made on one device. [[Identity]] [[Copied graphs]]
	- A snapshot plus an append-only log of updates, compacted now and then, so that a save doesn't rewrite everything. The shell's `AGENTS.md` says when that will be needed.
	- The derived indexes and full-text search in SQLite tables, which can be rebuilt from the document at any time and are never synced.
